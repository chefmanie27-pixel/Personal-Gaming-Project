# Transactional private-data restore design

Status: design for the next implementation increment. No restore write endpoint, schema change or apply button is enabled by this document. The existing preview remains advisory and local.

## Observed constraints

UserWorkspace.version covers workspace metadata, but library and normalized journal mutations do not share that revision. Checking that version alone cannot authorize a restore against an unchanged destination. An account export reads a consistent Repeatable Read snapshot; it does not lock future writes after the response. Exports also contain creation timestamps that vary on every read, so hashing the raw response would produce false conflicts. Current imports commit separate batches and must not be described as an atomic restore.

## Account prepare and confirmation

A future authenticated prepare operation should validate the complete bounded backup with server schemas before producing a plan. It must derive account ownership from authentication, accept no destination user ID, and disclose that this action uploads private backup content. The current read-only preview explicitly promises local processing; it cannot silently start uploading files. Require explicit account destination and fixed destination-wins policy.

Use deterministic canonical encoding of validated source data and authoritative destination state, including journal mode, library private fields, journal content/revisions and workspace metadata/version. Sort object keys and record sets deterministically; exclude only volatile export creation time and equivalent transport provenance. Bind the plan to authenticated user, source digest, destination digest, policy/schema version and short expiry using an authenticated server token. Do not use an unsigned client digest or stored backup revision as write authority. Responses and errors must use no-store and avoid logging private payloads.

The confirmation view must display the actual server plan counts and compatibility issues. A changed source, account, destination, expired token or failed read discards confirmation. Readable legacy IDs, snapshot extensions and fields incompatible with strict account schemas must cause an explicit compatibility result; never silently strip, trim or regenerate them. Any future conversion requires a separate reviewed mapping that also repairs references and avoids duplicates on retry.

## Account commit and conflict behavior

At commit, validate authentication, explicit consent, backup, plan authenticity/expiry and request byte/count limits again. Within one bounded Serializable database transaction, reread the complete destination, verify its digest and journal mode, compute additions with destination values winning, validate the resulting metadata/references/capacity, then write all additions and metadata together. Include full normalized history rather than loaded pages. No library, journal or metadata batch may commit separately.

Database uniqueness and collation determine conflicts. Exact JavaScript strings alone cannot model a case-insensitive database key. Inspect actual configured collation and test case variants on disposable MySQL. Ambiguous source keys or collisions must yield a reviewable conflict or validation result before any write; never reinterpret them silently. Do not assume that the local advisory counts are the final database plan.

Serializable isolation, predicate/range coverage and concurrent writer behavior must be proved with the actual repositories. A lock on UserWorkspace alone is insufficient because existing library/journal writers do not acquire it. Serialization failures, uniqueness races or deadlocks must roll back the whole transaction. Return a refresh-required conflict; never blindly rerun against a changed snapshot. Server limits must include transaction time, total encoded bytes, row counts and write volume. Never truncate records to fit.

Journal versions for newly restored rows are generated by the server; file revisions are provenance only. Existing rows, profile and ordinary destination preferences remain untouched. New collection/goal/watch/metadata/feedback/rule keys follow the reviewed destination-wins merge policy and are validated together. Legacy versus normalized migration must be a deliberate transaction step, with inconsistent mixed histories rejected. The simplest first release can reject legacy destination layouts with a clear compatibility response rather than migrate them implicitly.

## Retry and uncertain completion

Replaying an old confirmation after a successful commit must not apply anything twice: the destination digest changes and the old plan becomes stale. After a lost response, reload authoritative data and prepare a new plan; show which rows already exist. This provides conflict-safe reconciliation, not a promise that the client knows whether a timed-out commit succeeded. If durable receipt semantics are required, design and test a user-scoped idempotency receipt in the same transaction before release. Do not add a migration to an existing database as part of a fixture test.

## Device boundary

Two localStorage keys do not form an atomic transaction, and checking their values then writing both leaves cross-tab races and partial quota failures. Keep device apply disabled until a single authoritative transactional storage design or a tested recoverable commit protocol is implemented. Preserve original values and account/device separation. A storage event or focus-return invalidates the advisory preview; that is freshness feedback, not cross-tab locking.

## Required acceptance before enabling writes

- Disposable MySQL tests: all-or-nothing failure injected after library/journal writes; concurrent edits to every dataset; absent workspace creation; full normalized journal beyond 2,000 rows; user isolation; case/collation collisions; stale source/destination/policy/expired confirmations; bounded rejection without partial writes.
- Retry tests: successful commit with lost response, stale replay, fresh prepare after reconciliation and unchanged original source. Assert existing values are preserved and no duplicate rows are created.
- UI tests: explicit upload consent and account confirmation, pending duplicate suppression, current-account display, stale operation isolation, error/recovery behavior, focus and mobile layout. Preview alone never starts a write.
- Device restore requires separate cross-tab and quota/crash recovery evidence before activation. Production load, recovery and assistive-technology acceptance remain separate gates.
